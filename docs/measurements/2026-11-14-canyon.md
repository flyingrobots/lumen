# Measurement record: the canyon scene at 4K and 16 samples per pixel, 2026-11-14

This is a record of one session. It describes what was measured on the date above, at the
commit below. It is not a statement about any later commit. To repeat it, see the command below
or `make 4k-canyon` (which runs the same render with 8 CPUs by default; pass
`CPUS=18 MEMORY=12g`).

It answers flyingrobots/lumen#40: how large the canyon scene is, what its tree looks like, how
long its 4K render at 16 samples takes, with its image hash the same on every run, and what a
ray costs in it against the reference scene and Fixed Point, measured in the same session by
the same method.

## Image hashes

All three canyon runs, and the `--stats` run, printed:

```text
sha256:cbd020b9949ae7310b11fb21650e9336ca2e6ec99e0f2bcd950ff61d39469eab
```

Independent check of the three exported PNGs (each 33 188 430 bytes, 8-bit RGBA, filter type 0
on every row), on the host, without Lumen's code: Python's `zlib` decompressed the `IDAT` data,
the filter bytes were removed, and `hashlib.sha256` over the RGBA8 pixels gave that hash for all
three. The reference scene printed
`sha256:97d1d3034439186d6891a65cb6c2552945e5c9fc10fa584a83cfa6c28fdbebfe` and Fixed Point
`sha256:1c275a36ba5f18d2cb96392e006597ad7b87d0f1878682de75e8f0aac2eb8a05` on every run.

At 960 by 540 and 16 samples (22 298 953 rays) the canyon printed the same hash at 1 thread and
at 18, `sha256:5febad8baf2e6c1314635f53a0d1b0e06989ccf8c9a9d01ecce0a929398c2f69`: 11.298 seconds
of render on one thread (506.7 ns per ray), 0.862 on 18 (38.7), 13.1 times faster.

## What it says about traversal at this size

The canyon and the reference scene trace almost the same number of rays (356.8 against 355.3
million, with nearly the same split), so their times compare ray for ray: a canyon ray costs
40.7 ns on average at 18 threads, the reference scene's 15.0 and Fixed Point's 18.0, 2.7 times
the reference's. The canyon has 18 times the reference's triangles and its mean leaf depth is
2.8 levels deeper (19.13 against 16.36; a balanced tree would be 4.1 deeper for 17 times the
leaves), so depth alone does not explain the cost. Two readings, neither measured here:

- the scene is 258 MB against 11 MB, so the reference scene's tree and triangles stay in the
  processor's caches and the canyon's do not; and
- a heightfield canyon is hard for a bounding-volume tree: rays run along the floor and walls,
  close to many triangles, and the walls' boxes overlap the floor's, so each ray may visit many
  more nodes than the depth suggests.

Fixed Point's 18.0 ns against the reference's 15.0 includes its smooth hits and its own tree, so
it does not separate either effect either.

## What was not measured

- Nodes visited per ray, which would separate the two readings above: it waits for Bunny's
  counting traversals (flyingrobots/bunny#335).
- The split of `Scene::new` between the surfaces, the content identity and the tree.
- Any native (non-container) number, any other machine, more than one session.
- The 18 CPU runs use the VM's CPUs as the hypervisor schedules them; the three canyon renders
  spread over 0.45 seconds (3 %).
